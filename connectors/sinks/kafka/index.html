Kafka output connector

Feldera can output a stream of changes to a SQL table or view to a Kafka topic.

The Kafka output connector supports fault tolerance. Delivery, retries, and backpressure describes what the connector does when the broker is slow or down, what it reports, and the metrics it exports.

Kafka Output Connector Configuration​

PropertyTypeDefaultDescription
topic (required)stringThe Kafka topic to send to.
bootstrap.servers (required)stringA comma separated list of Kafka brokers to connect to.
headersarray of objectsKafka headers to be added to each message produced by this connector. A header specifies a key and, optionally, a value. The value must be a string or an array of bytes, e.g., [{"key": "key1", "value": "val1"}, {"key": "key2", "value": [1,2,3,4,5]}, {"key": "key3"}]
log_levelstringThe log level for the Kafka client.
initialization_timeoutduration60sMaximum time to wait for the connector to connect to a Kafka broker, for example 60s. Replaces the deprecated initialization_timeout_secs.
kafka_servicestringIf specified, this service is used to provide defaults for the Kafka options.
regionstringThe AWS region to use while connecting to AWS Managed Streaming for Kafka (MSK).
fault_toleranceobjectlibrdkafka options the connector uses when the pipeline runs with exactly-once fault tolerance. See Fault tolerance options.

The connector passes additional options directly to librdkafka. See relevant options for producers.

Fault tolerance options​

A pipeline configured for exactly-once fault tolerance writes to Kafka through transactions, which needs a consumer as well as a producer. fault_tolerance adds librdkafka settings for those two clients:

PropertyTypeDefaultDescription
consumer_optionsobject{}Options passed to librdkafka for consumers only, overriding the connector's other Kafka options.
producer_optionsobject{}Options passed to librdkafka for producers only, overriding the connector's other Kafka options.

fault_tolerance does not turn transactional writes on or off; the pipeline's fault tolerance model does. Omitting fault_tolerance leaves the consumer and producer with the connector's other Kafka options and the librdkafka defaults.

"fault_tolerance": {
  "consumer_options": {"fetch.max.bytes": "10485760"},
  "producer_options": {"compression.type": "lz4"}
}

Delivery, retries, and backpressure​

For pipelines without exactly-once fault tolerance, the connector defaults message.timeout.ms to 0: temporary broker failures are retried without a delivery deadline. When the producer queue fills, the connector waits for room. The controller's output queue then fills to max_queued_records, and the pipeline stops advancing until the sink catches up. Configure queue.buffering.max.messages and queue.buffering.max.kbytes to bound the producer queue; the byte limit takes priority. These bounds apply per connector.

To restore the former five-minute delivery deadline, add either "message.timeout.ms": "300000" or "delivery.timeout.ms": "300000" to the transport's config object. The two names are aliases; configure only one. An explicit finite timeout or retry count can cause undelivered records to be dropped. Permanent errors, such as a rejected oversized message, can also lose records. The connector reports these losses as errors. Shutdown does not guarantee delivery of records still in the non-fault-tolerant producer queue.

The connector reports unhealthy when a pending message has waited at least 10 seconds for delivery and no delivery completed in the last 10 seconds, or when a delivery fails. A slow broker that keeps acknowledging is not a stall, however long its queue. This check also runs on a quiet connector with spare queue capacity and when statistics are disabled. Records purged from the producer queue when the pipeline stops count as delivery errors in the metrics but are not reported as connector errors. Enqueuing another message does not establish recovery. A successful delivery restores healthy status only if no other message is overdue and the producer has no fatal error. After a fatal error, fix the underlying broker or configuration problem and restart the pipeline. Broker connection failures during an outage are logged as warnings. They are not counted as connector errors, because the queued records are retained.

These delivery defaults and health rules apply to the non-fault-tolerant sink. The exactly-once sink uses Kafka transactions, described next.

Exactly-once delivery and recovery​

With exactly-once fault tolerance, the connector writes each step's output in one Kafka transaction and commits it at the end of the step. The producer retries deliveries without a retry limit. A transaction that stays open longer than transaction.timeout.ms (60 seconds by default) fails on the broker side.

The connector keeps a copy of every record of the open transaction until the commit succeeds, because a transaction cannot be retried as it is: librdkafka fails a transaction at its first failed delivery, and the broker aborts a transaction older than transaction.max.timeout.ms (15 minutes by default). When a delivery fails or the commit reports that the transaction must be aborted, the connector aborts it, begins a new one, sends the kept records again, and commits. It repeats this, with a growing backoff of up to 10 seconds, until the commit succeeds or the pipeline shuts down. When only the commit call times out, the connector calls commit again and does not send the records again. Aborted attempts stay invisible to consumers that read with isolation.level=read_committed, so successfully committed records appear once.

A record that the client refuses for its own sake, such as one larger than message.max.bytes, is dropped and reported as a connector error, including when a replay first discovers the refusal. Other records in the transaction can still commit. A refusal by the broker, for example a batch larger than the topic's max.message.bytes, fails every record of the batch, so the connector cannot single out a record and drops nothing: it aborts and replays as after any other failure. When three aborts in a row, over at least five seconds, fail for a reason other than a delivery timeout, the connector reports a connector error once per transaction that names the reason, and keeps retrying. Besides a refused batch, this covers a revoked topic permission, a deleted topic, and a transaction whose output takes longer than transaction.timeout.ms to send and commit. For large steps, such as the first output after a snapshot, raise that option in the producer options, up to the broker's transaction.max.timeout.ms.

The kept records live in memory up to 64 MiB per connector and spill to an unnamed temporary file above that. The file is in the pipeline's storage directory when the pipeline has one on the local file system, and in the system temporary directory otherwise. It holds the output of the open transaction beyond the first 64 MiB, so plan for free space equal to the largest transaction's output, for example the first output after a snapshot or a backfill. The file goes away at commit. An I/O error on that file is fatal for the connector. A record refused by the client, such as an oversized message, is reported once and is not kept.

The connector reports unhealthy while it retries, aborts, or replays, and while a push waits for room in a full producer queue for more than 5 seconds. It reports healthy again after the next successful commit.

A fatal producer error, or a transaction error whose recovery action is unknown, is reported as a fatal connector error. One example is a fenced producer. Kafka fences a transactional producer when another producer starts with the same transactional.id (here the topic name): the broker then refuses all further writes from the older producer, so that only one instance can commit. The connector stops the pipeline's output thread and holds it until the pipeline is stopped: it never recreates a fenced producer, because that could fence the instance that owns the topic now. A broker can also fence a producer after its transaction expires during a long outage; that case requires a pipeline restart too. Fix the broker or deployment problem and restart the pipeline. On restart the connector reads the last committed position from the topic and skips the transactions that were already committed.

Commit and abort calls wait at most 10 seconds at a time. Shutdown is checked between calls, during retry backoff, and before each record sent during replay. The replay spool is retained until commit or connector teardown.

Output metrics​

The pipeline's /metrics endpoint exports the following metrics per output endpoint, for both sinks. Queue gauges and broker request counters refresh every statistics.interval.ms, which defaults to 10 seconds. With that option set to 0, those statistics are disabled and the corresponding metrics stay at their initial zero values. Delivery counters and health checks remain active. The full-queue wait counter updates during retries and when a wait ends, including cancellation; its refresh delay is at most the retry polling interval (5 seconds).

MetricTypeMeaning
kafka_output_queue_messagesgaugeMessages in the producer queue.
kafka_output_queue_bytesgaugeBytes in the producer queue.
kafka_output_queue_max_messagesgaugeConfigured message limit; zero means no message-count limit.
kafka_output_queue_max_bytesgaugeConfigured byte limit.
kafka_output_produce_retries_totalcounterBroker request retries, including metadata requests as well as produce requests.
kafka_output_request_timeouts_totalcounterBroker requests that timed out.
kafka_output_delivered_messages_totalcounterSuccessful delivery reports from librdkafka, according to the configured acknowledgement policy.
kafka_output_delivery_errors_totalcounterFailed asynchronous deliveries.
kafka_output_queue_full_wait_seconds_totalcounterTime spent waiting for producer queue space.

The exactly-once sink exports the same metrics, plus:

MetricTypeMeaning
kafka_output_transaction_aborts_totalcounterTransactions aborted and sent again after a delivery failure.
kafka_output_commit_retries_totalcounterCommits repeated after a retriable error or a timeout.
kafka_output_replay_spool_bytesgaugeBytes of the open transaction kept for replay, in memory and on disk.

Example usage​

We will create a Kafka output connector named total-sales. Kafka broker is located at example.com:9092 and the topic is total-sales.

CREATE VIEW v
WITH (
   'connectors' = '[
    {
      "transport": {
          "name": "kafka_output",
          "config": {
              "bootstrap.servers": "example.com:9092",
              "topic": "total-sales"
          }
      },
      "format": {
          "name": "json",
          "config": {
              "update_format": "insert_delete",
              "array": false
          }
      }
   }
   ]'
)
AS ...

Authentication & Encryption​

SSL with PEM keys​

"config": {
    "bootstrap.servers": "example.com:9092",
    "auto.offset.reset": "earliest",
    "topic": "book-fair-sales",
    "security.protocol": "SSL",
    "ssl.ca.pem": "-----BEGIN CERTIFICATE-----TOPSECRET0\n-----END CERTIFICATE-----\n",
    "ssl.key.pem": "-----BEGIN CERTIFICATE-----TOPSECRET1\n-----END CERTIFICATE-----\n",
    "ssl.certificate.pem": "-----BEGIN CERTIFICATE-----TOPSECRET2\n-----END CERTIFICATE-----\n",
}

PEM-encoded certificates can be passed directly in the configuration using ssl.*.pem keys.

Multiple certificates​

librdkafka only accepts multiple certificates when provided via ssl.certificate.location keys (file paths) rather than directly with ssl.certificate.pem.

This is documented in librdkafka issue #3225.

To work around this limitation, Feldera handles PEM-encoded certificates and keys by:

  1. Storing the value passed to ssl.certificate.pem into a file.
  2. Naming the file using the SHA256 hash of the data.
  3. Replacing the ssl.certificate.pem configuration option with ssl.certificate.location option that points to the newly saved file.

Example:

The updated configuration would look like:

"config": {
    ...,
    "ssl.certificate.location": "path/to/certificate.pem"
}

⚠️ If both ssl.certificate.pem and ssl.certificate.location are set the latter will be overwritten.

Connecting to AWS MSK with IAM SASL​

Example of writing data to AWS MSK with IAM SASL.

important
  • AWS credentials must either be set as Environment Variables or present in ~/.aws/credentials.
  • Ensure that the defined output topic either exists in AWS MSK or, automatic topic creation is enabled.
  • sasl.mechanism must be set to OAUTHBEARER.
  • security.protocol must be set to SASL_SSL.
  • When the sasl.mechanism is OAUTHBEARER, the AWS region for MSK must either be set via the environment variable AWS_REGION or the region field in connector definition as in the example below.

Other protocols and mechanisms aren't supported.


CREATE VIEW output
WITH (
   'connectors' = '[
    {
      "transport": {
          "name": "kafka_output",
          "config": {
              "bootstrap.servers": "broker-1.kafka.region.amazonaws.com:9098,broker-2.kafka.region.amazonaws.com:9098",
              "sasl.mechanism": "OAUTHBEARER",
              "security.protocol": "SASL_SSL",
              "region": "<AWS_REGION>",
              "topic": "<TOPIC>"
          }
      },
      "format": {
          "name": "json",
          "config": {
              "update_format": "insert_delete",
              "array": false
          }
      }
   }
   ]'
) AS SELECT * FROM input;

Example of writing data to GCP Managed Service for Apache Kafka with OAUTHBEARER.

important
  • Ensure that the defined output topic either exists in GCP Managed Service for Apache Kafka or automatic topic creation is enabled.
  • sasl.mechanism must be set to OAUTHBEARER.
  • security.protocol must be set to SASL_SSL.
  • oauth_provider must be set to gcp.
  • Google credentials are resolved from Application Default Credentials: a service account key or user credentials file (e.g., as set up by gcloud auth application-default login), or, on GKE with Workload Identity configured, the metadata server.
  • GCP Managed Kafka authenticates a named principal, which Feldera takes from the service account email in the credentials, or from the metadata server. Credentials that name no principal, including the user credentials written by gcloud auth application-default login, require the principal in the GOOGLE_MANAGED_KAFKA_AUTH_PRINCIPAL environment variable. Setting that variable also overrides the principal derived from the credentials.

Other protocols and mechanisms aren't supported.


CREATE VIEW output
WITH (
   'connectors' = '[
    {
      "transport": {
          "name": "kafka_output",
          "config": {
              "bootstrap.servers": "bootstrap.<CLUSTER>.<REGION>.managedkafka.<PROJECT>.cloud.goog:9092",
              "sasl.mechanism": "OAUTHBEARER",
              "security.protocol": "SASL_SSL",
              "oauth_provider": "gcp",
              "topic": "<TOPIC>"
          }
      },
      "format": {
          "name": "json",
          "config": {
              "update_format": "insert_delete",
              "array": false
          }
      }
   }
   ]'
) AS SELECT * FROM input;
